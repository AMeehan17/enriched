## Vision

### 10x Check

Current plan: 5 interactive modules + OG image sharing. A beautiful reference site for nuclear education.

**10x version:** Enriched becomes **the nuclear data layer for the internet.**

- Every module is also an embeddable widget (iframe-able, one line of code to drop into any site)
- Every data point has a canonical URL you can link to and cite
- Public JSON API that researchers, journalists, and other sites consume
- Every chart has a "Cite this" button that produces BibTeX citations
- Curated preset URLs serve as rebuttal-in-a-link for nuclear Twitter
- A "What if?" policy simulator lets users manipulate country energy mixes and watch consequences
- Time-travel sliders show how every metric evolved from 2010-2026
- Command palette (Cmd+K) for power users and fast discovery

The shift: Enriched stops being a site people visit and starts being infrastructure the internet routes through. When someone writes a nuclear article, their first stop is Enriched for the chart. When a researcher needs normalized data, they hit the API. When a nuclear advocate needs to end a Twitter argument, they drop a preset URL.

### Platonic Ideal (VISION, not v1)

This section is aspirational. Nothing in it is committed scope. It exists to keep us oriented toward the 12-month destination while we build v1.

The best engineer in the world with unlimited time and perfect taste would build:

- **Every reactor has a profile page.** Live status from PRIS API. Construction photos. Operating history. Notable events. Cultural significance. Related reactors. An RSS feed per reactor. (Vision)
- **Every dataset has a canonical endpoint** with confidence intervals and historical trajectory. (Partially v1 via API; confidence intervals are vision)
- **Every comparison has a shareable URL.** Every URL has an OG image. (v1)
- **The site has a heartbeat.** Monthly data refresh, weekly pulse, annual "state of nuclear" report pinned to the home page. (Vision)
- **Embedding is one line** via a script injector (`<script src="enriched.xyz/embed.js">`). (Vision — v1 uses iframe routes, see Embed Model below)
- **Accessibility is lived, not checklisted.** (v1 baseline: WCAG 2.1 AA)
- **The data is better than anyone else's.** Curated, normalized, cited, and fresh. Researchers cite Enriched instead of chasing primary sources. (v1 aims toward this but will not match OWID depth on day one)

The emotional experience: a smart person lands on Enriched and 30 seconds later is forwarding a URL to a friend with "look at this."

## Accepted Scope — Detailed Specs

### Module 1: Energy Source Comparison (expanded)

Base features from design doc (6 sources, 8 dimensions, animated bars, OG images, mobile responsive, accessibility). Additions below.

#### URL State Schema

```
/compare?sources=nuclear,solar&normalize=nuclear&year=2024&preset=climate-case
```

- `sources`: comma-separated source IDs (nuclear, solar, wind, gas, coal, hydro)
- `normalize`: single source ID or `none` (default: `none`)
- `year`: integer 2010-2026 (default: 2024)
- `preset`: optional preset slug that overrides other params when present

All params are bookmarkable and drive OG image generation.

#### Normalize to Any Source

Dropdown replaces the original boolean toggle. Options: `None | Nuclear | Solar | Wind | Gas | Coal | Hydro`. URL param: `normalize=<source-id>`. When set, every bar displays its value as a multiple of the baseline source's value for that dimension. Disabled state when fewer than 2 sources are selected.

**Divide-by-small-number guard:** Per-dimension minimum threshold. If the baseline source's value for a dimension falls below the threshold (e.g., deaths per TWh for wind ~0.04), normalized display for that dimension falls back to **absolute values** with a small footnote: "Baseline too small to normalize meaningfully — showing absolute value." Per-dimension thresholds defined in the data file. Prevents absurd multiples like "2000x" from appearing in the UI.

OG images reflect the chosen baseline in the card layout ("Normalized to Solar" badge when applicable).

#### Data Time Machine

Year slider 2010-2026 above the comparison grid. Animated bar transitions on year change using Framer Motion (respecting `prefers-reduced-motion`).

**Data sourcing (honest assessment — this is real work):**
- LCOE: Lazard LCOE reports v3-v17 (2010-2024). Discrete annual reports, machine-readable tables available. Nuclear and renewables well-covered; hydro sparse.
- Capacity factor: EIA Electric Power Monthly (US only, historical series). International data via IEA Electricity Information (paywalled for some years — may need to interpolate or use country averages).
- Lifecycle CO2: IPCC AR5 WG3 Annex III is a snapshot, not a time series. Use a static median value and add an editorial note that lifecycle emissions change slowly.
- Deaths per TWh: Markandya & Wilkinson (2007) + OWID updates. Updated sparingly — treat as near-static with occasional updates.
- Land use: Brookings / academic studies. Near-static.
- Energy density: Physical constant, not time-varying.
- Construction time: IAEA PRIS historical database. Available per project start.
- Dispatchability: EIA capacity credit, near-static.

**Reality check:** Only **LCOE** and **capacity factor** have genuine annual time series. The other 6 dimensions are effectively static or updated every 5-10 years. The time machine ships honestly:
- **LCOE and capacity factor** animate on year change (real time series data)
- **The other 6 dimensions** show static lines with an editorial note: "This dimension does not change meaningfully year-over-year" with a small info icon explaining why.
- This solves the "preset + time machine interaction" problem flagged by the outside voice — presets that focus on static dimensions (like `fear-of-nuclear` focused on deaths per TWh) simply don't animate across years, which is the truthful behavior.

**Preset-time interaction:** Each preset declares which dimensions are its "highlighted" ones. If those dimensions are all static, the year slider is disabled when that preset is active, with a note: "This preset's data does not vary year-over-year."

Data compilation budget: **~6 hours** for LCOE (Lazard v3-v17 is well-structured) and capacity factor (EIA series, US-focused but sufficient). Plus ~2 hours for static values on the other 6 dimensions with full citation objects. Total: ~8 hours of data work for Module 1.

For dimensions with sparse pre-2015 data (hydro LCOE, non-US capacity factors): slider scale starts at 2015 for those dimensions specifically. The slider itself always shows 2010-2026 but values before first-data-year display as "Data not available" in the bar.

For these presets, the year slider is **enabled** but the static-dimension bars do not animate on year change. An info icon on each static bar explains why. The slider's effect is visible only on the varying dimension(s).

#### "Cite This" (BibTeX only for v1)

**Citation schema upgrade (prerequisite):** The current data schema has a simple `source` string like "Lazard LCOE v16.0 midpoint." This is not enough to generate valid BibTeX. Restructure:

```json
"lcoe": {
  "value": 141,
  "unit": "$/MWh",
  "citation": {
    "bibtex_key": "lazard2024lcoe_nuclear",
    "author": "Lazard",
    "title": "Levelized Cost of Energy Analysis, Nuclear Row",
    "year": 2024,
    "version": "v16.0",
    "publisher": "Lazard Ltd.",
    "url": "https://www.lazard.com/research-insights/levelized-cost-of-energy-version-16/",
    "accessed": "2026-04-09"
  }
}
```

**BibTeX key uniqueness:** Keys must be unique across the entire dataset. Pattern: `{author}{year}{shortname}_{source-id}` — e.g., `lazard2024lcoe_nuclear`, `lazard2024lcoe_solar`, `ipcc2014ghg_nuclear`, `ipcc2014ghg_solar`. Validated at build time by a script that diffs the set of keys and fails if any duplicate.

Every data point carries a complete citation object. The cite-this button generates a BibTeX entry from this object.

**v1 ships BibTeX only.** APA and MLA are deferred to TODOS.md. BibTeX is the academic default — it's the format that matters most for the "researchers cite Enriched" hypothesis, and shipping one format correctly beats shipping three formats hand-wavily.

This schema change is a **prerequisite** for the cite-this feature. It must happen before the citation UI is built. Add ~2 hours to the data compilation budget for the schema upgrade.

#### Embed Variant

**Embed model for v1: iframe routes, NOT script injector.**

`/embed/compare` (and `/embed/reactors`, `/embed/fuel-cycle`, etc.) are dedicated routes that render the module with a compact layout (no nav, no footer, small "Made with Enriched" attribution link). Query params drive state the same way they do on the main routes.

**Embed spec:**
- Default dimensions: 640×480 (widescreen) or 480×640 (portrait)
- URL params: `?sources=...&normalize=...&year=...&theme=light|dark`
- `theme=dark` supported even though the main site is light-mode default — embeds need to fit host sites
- HTTP response headers:
  - `X-Frame-Options` NOT set (must allow cross-origin embedding)
  - `Content-Security-Policy: frame-ancestors *` for explicit permission
  - `Cache-Control: public, max-age=3600` (embeds can be cached)
- Responsive: embeds resize to container width, min 320px, max 1200px
- `postMessage` API for host sites: embed emits `{type: "resize", height: N}` so host can auto-size iframe

**Not in v1:** The `embed.js` script injector is deferred. Iframe is simpler, more compatible, and sufficient for the launch hypothesis. Revisit once we see how people embed.

### Module 6: "What If?" Policy Simulator (DEFERRED — vision spec, not Ship 1)

**This entire section is a vision spec for a module that ships AFTER Ship 1 feedback validates the core design principle.** Retained here so the architectural implications (country data model, first-order cascade math, methodology page) are preserved for the eventual build. Do not start this work before Ship 1 has 10 humans of feedback.


**Data sourcing for Module 6 (country energy mix):**
- Primary source: IEA World Energy Balances (per-country, per-year generation by source). Available as downloadable CSV from iea.org (free for basic data, paywalled for extended series).
- Alternative: Our World in Data's country energy dataset (MIT-licensed, machine-readable, good enough for 2010-2024 across the 8 countries).
- Compilation budget: ~4 hours for the 8 countries × 6 sources × recent year snapshot. Historical time series optional for v1 — the simulator works on current-year data.
- Output: `countries.json` file with per-country energy mix, populated from OWID (with attribution).

**Countries (v1 ships with these 8):**

| Country | Why | Current nuclear share |
|---------|-----|------------------------|
| Germany | Post-nuclear-shutdown case study, counterfactual power | 0% |
| France | The pro-nuclear baseline | ~65% |
| United States | Largest nuclear fleet globally | ~19% |
| Japan | Post-Fukushima recovery trajectory | ~7% |
| South Korea | Successful nuclear buildout + KEPCO exports | ~30% |
| United Kingdom | SMR frontier + Hinkley Point C | ~15% |
| China | Fastest nuclear buildout globally | ~5% |
| India | Fastest-growing electricity demand | ~3% |

**Calculation model (explicitly first-order, labeled as such in UI):**

The simulator uses **linear emission-factor arithmetic**. When the user drags "replace 20% of coal with nuclear," the model:

1. Takes 20% of the country's coal generation (TWh/year)
2. Replaces that with nuclear generation
3. Recomputes CO2 emissions using source-level emission factors (gCO2/kWh × TWh)
4. Recomputes deaths using source-level death rates (deaths/TWh × TWh)
5. Recomputes land use using source-level coefficients
6. Recomputes blended LCOE as a weighted average

**This is not a real energy-systems model.** It ignores grid stability effects, intermittency balancing, transmission constraints, retirement schedules, build times, and dispatchability interactions. The simulator must prominently label its outputs as **"First-order estimates — illustrative, not policy-grade"** with a link to a methodology page explaining what the model includes and excludes.

**Why linear arithmetic is enough:** The educational value is in the *direction and magnitude* of the cascade, not in precision. A viewer dragging Germany's coal to nuclear and seeing "~1,100 fewer air pollution deaths per year" is learning something true even if the real number is ±30%. But we must be honest that it's an estimate, and the UI must wear that honesty on its sleeve.

**Acceptance criteria for Module 6:**
1. All 8 countries selectable
2. Sliders for coal→nuclear, gas→nuclear (each 0-100% of current share)
3. Real-time cascade of: CO2 (MT/year), air pollution deaths (per year), land use change (km²), blended LCOE ($/MWh), total nuclear share of generation (%)
4. Every output carries a "first-order estimate" tag in the UI
5. Methodology page linked from the simulator explains the model and its limits
6. "Share this scenario" button generates a URL with full state encoded
7. OG image for shared scenarios shows the before/after cascade as a static card
8. Accessibility: keyboard-navigable sliders, screen reader announces values on change
9. Mobile responsive

**Effort budget:** 15-20 CC hours (up from the earlier 6-8 estimate). The increase accounts for: the honest methodology page, explicit UI labeling, data sourcing for all 8 countries, and the OG image template.

### Cross-Cutting Infrastructure

#### Ship 1: Static JSON Files (not an API)

Ship 1 serves data as stable CDN-cached JSON files, not a versioned API:

- `/data/sources.json` — full source dataset with all dimensions, citation objects, and time-series arrays for LCOE and capacity factor
- `/data/presets.json` — the 5 Ship 1 presets with their structure

Both files have `Cache-Control: public, max-age=3600, stale-while-revalidate=86400`. Researchers and journalists can `fetch()` them. The `/docs/data` page documents the schema and provides example usage. No rate limiting, no versioning path, no Upstash dependency. If someone asks for a real API later, build it then.

**Future API path (DEFERRED — vision spec, not Ship 1):**

The section below documents what a versioned public API would look like if usage patterns eventually justify building one. It is NOT shipped in Ship 1. Retained here for architectural continuity if Ship 1 feedback shows demand for programmatic access beyond static JSON.

#### Public JSON API (DEFERRED — vision spec)

**Routes:**
```
GET /api/v1/sources                          List all energy sources
GET /api/v1/sources/{id}                     Full source data with all dimensions and citations
GET /api/v1/sources/{id}/{dimension}         Single dimension value
GET /api/v1/sources/{id}/{dimension}?year=N  Historical value for a specific year
GET /api/v1/reactors                         All reactor designs
GET /api/v1/reactors/match?fuel=u235&coolant=water   Filter endpoint
GET /api/v1/fuel-cycle/steps                 Fuel cycle data
GET /api/v1/countries                        List all countries (id, name, nuclear share)
GET /api/v1/countries/{id}                   Full country energy mix — { generation: { nuclear: TWh, coal: TWh, gas: TWh, solar: TWh, wind: TWh, hydro: TWh, other: TWh }, year, citation, lastUpdated }
GET /api/v1/presets                          List all preset definitions
```

Every response includes:
- `data` — the actual payload
- `citation` — structured citation object (BibTeX-compatible)
- `lastUpdated` — ISO timestamp of last data refresh
- `apiVersion` — "v1"

**Rate limiting:**
- **Upstash Redis** for counter storage (Vercel KV is also acceptable; Edge Config is NOT — it's read-optimized and cannot handle counter writes). Acknowledged: this would introduce a lightweight backend dependency, breaking the "no backend" premise of the design doc. **Ship 1 avoids this entirely** by using static JSON files instead. This spec only applies if the API path is eventually built.
- 100 requests/minute per IP, free tier, no key required
- Return `429 Too Many Requests` with `Retry-After` header when exceeded
- No authentication in v1 (the `Authorization: Bearer` header speculation has been **REMOVED** — it was YAGNI)

**Documentation:**
- OpenAPI 3.0 spec at `/api/v1/openapi.json`
- Human-readable docs at `/docs/api` (can be generated from OpenAPI)

**OG Image Caching Strategy (critical for feasibility):**

Satori (@vercel/og) has CSS subset limitations and OG generation is not free. Every unique URL param combination mints a cached OG image on the Vercel bill. Without abuse protection, an attacker could generate millions of cached images by iterating params.

Strategy for Ship 1 (Module 1 only):

1. **Static OG images** for the home page, Module 1 landing page, each preset, and the about page. Generated at build time, served from CDN. Zero per-request cost.
2. **Dynamic OG images** for shared comparison URLs (`/compare?sources=...&normalize=...&year=...`) with strict **param validation** before generation:
   - `sources`: must be subset of the 6 known source IDs
   - `normalize`: must be one of the 6 source IDs or `none`
   - `year`: must be integer 2010-2026
   - Any invalid param → serve the static Module 1 fallback card (no generation)
3. **Cached aggressively** with `Cache-Control: public, max-age=604800, immutable` keyed on the validated URL. Vercel's edge cache handles this.
4. **Abuse budget:** The validated param space is small (6 sources × 2^6 combinations × 7 normalize options × 17 years ≈ 76,000 possible images). That's a manageable upper bound on total cached generations. If observed generation rate exceeds ~100/hour, add exponential backoff or disable dynamic generation temporarily.
5. **Fallback static card** if the dynamic generator fails or times out. Every OG route has a fallback.
6. **Satori-compatible layout only:** flexbox, text, rectangles, images. No complex SVG, no animations. Design within Satori's constraints.

Realistic time budget: **~6-8 hours** for the validation + caching + fallback + debugging the first Satori weird edge case (fonts, emoji, image embedding). Not 2-3 hours.

## Future Monetization Path (NOT committed)

The user raised the possibility of monetizing the API during the CEO review. Worth capturing as strategic direction without committing now.

**Pattern:** "Free for humans, paid for machines at scale."

- Individual researchers, students, journalists, bloggers, Twitter users → unlimited free access, no API key required
- High-volume commercial consumers (companies building products, internal tools at energy firms, data aggregators, SaaS dashboards) → paid API keys with SLA, higher rate limits, webhook updates

**Architectural implications for Ship 1 (what the static-JSON approach preserves for future monetization):**
1. Stable URLs at `/data/sources.json` can eventually migrate to `/api/v1/sources` without breaking consumers if a redirect is added at that time.
2. Static JSON files cost essentially zero to serve via Vercel's CDN — no cost wall that forces monetization early.
3. If and when a real API ships later, THAT is where rate limiting + optional auth for paid tiers can live. Ship 1 doesn't foreclose any of this, it just doesn't build it speculatively.
4. Frontend, preset URLs, OG images, and static JSON stay free forever regardless of future API monetization.

**Removed from earlier draft:** The "optional Authorization: Bearer header that currently does nothing but gets logged" idea. That was YAGNI — no need to build auth plumbing before there's a real paying consumer. Versioning the URL path is sufficient future-proofing.

Decision on whether to actually monetize can wait 6 months until API usage patterns are visible.

**Do NOT build a billing system now.** Ship 1 uses static JSON files at stable URLs, which preserves the option to build a monetizable API later without breaking any existing consumers.
